# TG 短剧媒体库

用 Go 实现的 Telegram 短剧媒体库：扫码或手机号登录账号，自动采集多个短剧频道的视频，按「剧名 + 集数」聚合，提供类似视频网站的竖屏 H5 播放页——卡片墙、标签分类、本地搜索、选集播放，并支持同一集在不同频道线路之间切换。

## 功能特性

- **扫码 / 账号登录**：PC 默认扫码（手机 Telegram 授权），手机端默认手机号 + 验证码，两种方式随时切换；官方桌面凭证登录时验证码走 Telegram App 内服务消息投递；支持两步验证密码，session 本地持久化，只需登录一次
- **历史回填 + 持续更新**：登录后自动分页拉取频道全部历史视频入库；之后常驻监听新消息，新集自动入库
- **短剧智能聚合**：剧名优先取发布者打的 `#剧名` 标签（比正文标题可靠：正文常写错、带「黄豆自制版」等后缀），标签里的分类词（`#剧情 #真人 #日常` 等 60 多个）会被跳过，取第一个真正的剧名标签；没有可用标签时才回退到 `《》`/【】标题。集数支持 `第N集 / EP01 / 1-10集 / 中文数字`，只解析标题区——`剧情介绍：…更新到第十集`、`第049期`、`EP72分02秒`、`第二季` 都不会被当成集号，营销长文不建剧
- **多线路合并**：同一集在不同频道的来源合并为不同线路；每集可能包含多段视频，顺序连播
- **自动换线路**：某段播放失败自动切下一段，整条线路失败自动切下一线路，也可手动切换
- **标签分类**：消息中的 `#标签` 自动提取为分类，泛化词（`#ai短剧` 等）不参与分类
- **列表排序**：搜索框下方、「收藏」按钮后面有排序切换，默认 `自然↑` 保持接口默认顺序（首页按最近更新、收藏页按最近收藏）；点一下变 `集数↓`，按可播集数从多到少排（集数相同仍按时间），首页与收藏页走接口 `sort=episodes`，历史与搜索在前端按 `ep_count` 倒序；选择记在 `localStorage` 里，刷新后保持。
- **只显示可播短剧**：列表与标签计数只保留「有可播放视频」的短剧；空壳剧、纯广告帖、文件名当剧名的「完整1」都不会出现在首页。只有 1 集、名字又明显不是短剧的条目（演唱会、广告视频、众筹贴、美图/视频消除工具、宣发物料、片花、漫展街拍 vlog）标记 hidden 从列表隐藏；正常短剧即使只发了一集也照常显示。hidden 只是「不进列表」，搜索仍能搜到、详情仍能打开（数据保留）
- **快速加载**：列表页标签一次批量查询（30 部剧从 31 次查询降到 2 次），播放页一次请求同时拿到选集，封面/预览图带 24 小时缓存
- **本地搜索**：搜索只查本地数据库，实时返回，不访问 Telegram
- **播放历史**：自动记录每集播放进度（每 10 秒 / 暂停 / 切集 / 关闭页面时上报），看完自动标记；按短剧聚合，首页「继续观看」一键续播，可单条删除或清空
- **选集搜索补全**：详情页「🔍 搜索补全」按 `#剧名`、频道内搜索、纯剧名三轮找回缺失的集（没有空洞也强制搜、相册成员整组回捞、同一条消息只入库一次）
- **收藏**：详情页一键收藏/取消，首页「收藏」标签页单独浏览；收藏剧有新集时会提示更新（见下方「收藏更新提醒」）
- **首次使用引导**：首次登录且没有已启用的频道时，自动弹出「加入推荐频道」引导——一键加入全部推荐短剧频道（已加入的自动跳过），MTProto 直连加入，无需跳转 Telegram；点「暂不加入」后不再自动弹出，若随后没有任何已启用频道，首页常驻提示「请先加入或者启用短剧类频道」，可随时点「去加入」重新打开引导；一旦有了启用的频道就不再打扰。加入的频道立即入库、启用并回填历史
- **关闭频道立即生效并释放空间**：停用频道后该频道的来源不再计入剧库——列表、标签、搜索、收藏、详情与播放线路一并隐藏，且所有采集路径（历史回填、实时更新、搜索补全）在入库入口统一拦截；同时删除该频道已入库的来源、预览图与因此变空的剧集/剧，连本地缓存文件一起清掉并 `VACUUM`（重新启用后从头同步）。账号里已经退出的频道会在刷新频道列表时自动清理，不会一直显示「已启用」
- **封面自动修复**：封面回填遇到 `FILE_REFERENCE_EXPIRED` 时，重新拉取来源消息拿最新 `file_reference` 再下载，不会因为入库时的引用过期而永久缺封面
- **倍速播放**：播放器支持 0.75x / 1x / 1.25x / 1.5x / 2x 一键切换，选择会记住
- **清晰度选择**：对齐 Telegram Web——Telegram 在 `alt_documents` 里带了多清晰度版本时，播放器右侧出现「清晰度」入口，菜单为 `自动` + 各档位（1080P/720P/480P，按短边像素标注，同一分辨率多编码只留浏览器能播的一档）；**没有多版本时入口完全不出现**。默认自动：按播放窗口高度 × 像素比选「够用的最小一档」，全屏/窗口变化时自动重选；手动切换保持播放进度，切集/切线路后回到自动。数据在入库时随消息一并落库（`source_variants` 表），历史来源在播放页首次打开时补查一次（每来源只查一次，失败有 2 分钟冷却）；取流按文档隔离（缓存键与 ETag 均带 doc_id），切清晰度不会串版本
- **video.js 播放器**：内置 video.js 当内核（本地 embed，离线可用），控件全部自绘，排版与交互对齐 lanmei-duanju 的竖屏播放页：顶部返回/集数、右侧倍速/清晰度/追剧/线路/全屏、底部剧名与选集条、可拖动进度条；暂停时单击直接播放、播放中单击唤出控件、快速连点暂停、长按 3 倍速快进（松手恢复，纯文字提示）、上下滑切集、**左右滑改变播放进度**（拖动实时预览时间，松手一次 seek 不打断网络）
- **自动清晰度默认中等**：TG 提供多清晰度时默认取中间档（两档取低、一档唯一），均衡画质与流畅；手动切换后按所选档位播放，失败自动降档重试
- **横屏全屏翻转**：横屏视频进入全屏时自动锁定横屏方向（Screen Orientation API，退出全屏恢复自动旋转），不再出现「播放器全屏但画面竖着」的情况
- **线路切换**：播放器右侧「线路」列出同一集在不同频道的版本（频道名、时长、分辨率、大小），选中后固定从该频道拉流并保持当前进度；播放失败时也可直接跳转线路面板
- **单线程流式读取**：播放固定单线程顺序读取，Telegram Web 端并发读块不会提速，反而容易触发风控限流
- **CDN 分发支持**：Telegram 把部分大文件转移到 CDN DC 分发（旧版直接报「暂不支持在线流式播放」）。现在完整实现官方 CDN 协议：按 `dc_id` 建立带 CDN 授权握手的 CDN DC 连接、按 1MB 窗口对齐分片读取、AES-256-CTR 解密（IV 后 4 字节 = offset/16）、sha256 分窗校验、`FILE_TOKEN_INVALID` 自动回主 DC 重取令牌、`ReuploadNeeded` 自动请求主 DC 重传
- **首块快启**：块 0 固定 128KB（moov 在前部），首帧出画只等 128KB；续播/拖动从块中间进入时先拉 ≤128KB 快启段出画再补齐整块，不再等整块 1MB
- **边播边落盘**：播放的块同时写入磁盘缓存（`data/mediacache/doc_<docID>/`，位图索引 `index.json` 记录块序号→字节数），重启后索引仍有效；整集缓存完成后重播=本地播放（0 网络请求）。配额 `stream.disk_cache_mb`（默认 2GB），超限按「最久未访问的来源文档」整组淘汰；频道管理面板可查看占用并一键清理
- **直连优先**：公开频道的 ≤20MB 文件（t.me 网页版有官方转码直链，支持 Range/跨域/无 Referer 校验）播放时 302 直达 Telegram CDN，不占插件带宽与账号限流额度；抓取失败或大文件自动回退 MTProto 中转
- **流水线预读 + 头部固定缓存 + 1MB 块**：单次 upload.getFile 用满官方 1MB 上限（请求数较 512KB 减半）；写块给浏览器的同时后台预读下一块（有效并发仍为 1），网络往返与写块/浏览器消费重叠，高 RTT 代理下连续播放不再逐块等往返；每个来源的头两块（moov 所在）固定缓存不参与淘汰（最近 8 个来源，约 8MB），换清晰度/换线路/重试的重新起播省一次完整头部往返
- **播放期后台退让**：正在播放时封面/预览图下载全部暂停（退出播放自动恢复），把带宽与限流额度让给播放取流，降低播放中撞 FLOOD_WAIT 的概率
- **限流倒计时恢复**：撞上长 FLOOD_WAIT 时不再报「播不了」，服务端返回 503 + Retry-After，播放器显示「Telegram 限流中，N 秒后自动恢复」并倒计时原地续播（保进度），避免重试风暴加剧限流
- **选集取最长正片**：同一集混有短预告片时优先时长最长的视频；同长度时取文件大小居中的版本（不选最大、也不选最小），避免高码率版本拖慢网页拉流
- **不在本地保存视频**：播放全程走 Telegram 流式代理与 Range 请求，下载队列不再落盘视频；本地只保留数据库、封面、预览图与图片缓存
- **数据库只做索引**：`raw_messages` 的文档信息只保留定位字段（ID、access_hash、file_reference、体积、类型、尺寸、时长），不存内联缩略图字节与冗余标记；单条平均 890B → 310B，39MB 的库压到 26MB。`tgdrama.exe -compact` 可在不连 Telegram 的前提下单独做一次瘦身
- **图片一律走缓存**：有封面就发本地文件；没有封面（或文件被清掉）时生成一张带剧名首字的占位图，写到 `data/cache/` 后复用，列表里不会出现空白或破图
- **点击图片全屏放大**：详情页预览图/封面点一下全屏查看（双击缩放、双指缩放、左右滑动切换）；封面 ▶ 与播放按钮直接全屏起播
- **单二进制部署**：前端已 embed，Go 编译产出单个可执行文件

## 快速开始

### 1. 连接方式（标准 MTProto）

本项目使用标准 MTProto 客户端：TCP 直连 Telegram DC（可经代理），凭证由配置提供。默认内置 Telegram Desktop 官方应用凭证（`api_id 2040`）——**官方凭证登录时，验证码通过 Telegram App 内的官方服务消息投递**，不用等短信；使用 `my.telegram.org` 自申请的第三方凭证只能走短信，国内手机号短信投递经常失败（表现为「验证码收不到」）。

`telegram.api_id` / `telegram.api_hash` 可在 config.yaml 覆盖内置默认；多套部署共用同一凭证可能触发 `API_ID_PUBLISHED_FLOOD` 限流，被限时换自己的凭证即可。原先的 Telegram Web 端链路（`wss://*.web.telegram.org/apiws` + 公开 Web 凭证）与扫码登录已移除。

### 2. 编写配置

```bash
cp config.example.yaml config.yaml
# 编辑 config.yaml：确认代理地址；网络可直连 TG 时把 proxy 留空
```

配置说明：

| 字段 | 说明 |
|---|---|
| `telegram.api_id` / `telegram.api_hash` | Telegram 应用凭证，不填用内置默认（Telegram Desktop 官方应用） |
| `telegram.proxy` | 代理地址，如 `socks5://127.0.0.1:7890` 或 `http://127.0.0.1:7890`，直连可用则留空 |
| `telegram.transport` | 主连接传输：`auto`（默认，WebSocket 优先、失败回退 TCP）/`tcp`（IP 直连优先，配代理时推荐）/`ws`（只用 WebSocket） |
| `server.listen` | Web 监听地址，默认 `:5278` |
| `data.dir` | 数据库、session、视频、封面的存储根目录 |
| `stream.chunk_kb` / `cache_mb` | 在线播放的读块大小与内存缓存上限 |

### 3. 启动

```bash
go run ./cmd/tgdrama                 # 开发运行
# 或编译后运行
go build -o tgdrama ./cmd/tgdrama && ./tgdrama
```

### 4. 登录

浏览器打开 `http://电脑IP:5278`，未登录时会自动弹出登录层（也可点顶部横幅「去登录」再次打开），按设备默认选「扫码 / 账号登录」，可随时切换：

**扫码登录（PC 默认）**

1. 打开手机 **Telegram → 设置 → 设备 → 扫码**，扫描页面二维码并确认；不依赖 `auth.sendCode`，不受验证码限流影响
2. 若账号开启两步验证，页面会提示输入密码
3. 登录成功后自动进入媒体库，历史回填在后台进行

**账号登录（手机默认）**

1. 填带国家码的手机号（如 `+8613800138000`），点「获取验证码」
2. 验证码通过 **Telegram App 内的官方服务消息**投递（打开 Telegram App 看「Telegram」官方账号的消息），填进验证码框点「登录」；没有已登录的 Telegram 设备时才走短信
3. 若账号开启两步验证，页面会提示输入密码；验证码输错只提示重试，不会中断连接

登录会话保存在 `data/session.json`，只需登录一次；进程重启自动恢复登录。

> **同一个 `session.json` 只能给一个实例用。** 把 PC 的 `data/` 拷到手机/第二台电脑上
> 会让同一个 auth key 从两个 IP 同时连 Telegram，服务端会判定判重并注销这条会话
> （表现为 `AUTH_KEY_DUPLICATED` / 突然掉登录），每台设备各自登录一次即可。
>
> 会话也有可能被 **Telegram 侧注销**（在别的设备上点了退出登录、或账号被风控下线）。
> 这时所有 RPC 都会返回 `AUTH_KEY_UNREGISTERED`：客户端会自动清掉本地会话、回到扫码/
> 手机号登录界面，并在登录层提示「登录会话已被 Telegram 注销」，不需要手动删文件。

### 5. 观看

- 首页卡片墙浏览全部短剧，顶部标签按 `#标签` 过滤
- 搜索框输入剧名，实时返回本地结果
- 点击卡片进入详情看简介与选集，点击集数进入播放
- 播放失败会自动切换线路，也可用右上角下拉框手动选线；一集结束自动连播下一集
- 播放进度自动保存，下次进入同一集从上次位置继续；首页顶部有「继续观看」「收藏」「历史」入口

## 数据存储

```
data/
├── tgdrama.db          # SQLite 索引（剧/集/线路/标签/原始消息定位信息）
├── session.json        # TG 登录会话（敏感，注意保管）
├── covers/             # 视频封面（ffmpeg 抽帧 / 缩略图）
├── photos/             # 剧集预览图
├── cache/              # 图片缓存（没有封面时生成的占位图）
└── media/
    └── <剧ID-归一化名>/
        ├── 第1集-段0.mp4
        └── 第1集-段1.mp4
```

原始消息只留「怎么把文件取回来」的索引字段（文档 ID、access_hash、尺寸、时长），不留内联图片字节。解析规则升级后仍可基于本地数据重新解析，无需重新拉取 Telegram。

## 打包成 Go 插件（Android）

插件宿主（HikerView 等）要求 zip 根目录放 `plugin.json` + 一个 ELF 二进制，启动后读 stdout 的 `[jk] port=NNNN`，再访问 `http://127.0.0.1:NNNN/`。本仓库内置同样的打包流程：

```bash
python pack.py            # 只编 Android arm64 → tgdrama-plugin.zip
python pack.py --windows  # 同时编 Windows 版，方便桌面调试
```

打包脚本会：
- 用 `GOOS=android GOARCH=arm64 CGO_ENABLED=0` 编译 `dist/tgdrama-android`（`-trimpath -ldflags "-s -w -buildid="`），并校验 ELF 魔数
- 生成 `tgdrama-plugin.zip`（`plugin.json` + `tgdrama-android`，755 可执行位），打印大小与 md5
- 导出根目录 `tg-drama-rule.html`：与内置首页同一份，只多一行 `window.__TG_RULE_HOST__ = true`（侧载页据此把播放推给宿主，内置页不推）
- `plugin.json` 的 `desc` 固定为一句「Telegram 短剧媒体库：自动采集、多清晰度、CDN 分发播放、边播边落盘、限流倒计时恢复」，不要扩写
- **zip 里用 zopfli 重新压缩**：Python 的 `zipfile` 只能用自己的 deflate（zlib -9），手写 ZIP 头 + `zopfli.zlib` 的 raw deflate 流后，25.6MB 的 ELF 从 8.60MB 压到 8.25MB（再省 4%），整个包 8.82MB → 8.25MB；没装 zopfli 时自动退回 zlib -9，结构不变（method 8，Java/Android 解压无差异）

运行参数（见 `plugin.json` 的 `params`）：

```
-port 5278 -bind 127.0.0.1
```

宿主会额外传 `-data <getFilesDir()>` 指定数据目录；端口被占用时自动向后顺延，并把实际端口写入 `<data>/port.txt`。没有 `config.yaml` 时使用内置默认配置（含默认 Telegram 凭证）。Android 上没有 ffmpeg，封面抽取会失败，不影响播放。

连接层针对移动网络做了几件事：
- 连接/握手各有 15 秒超时，连不上会在 25 秒后把错误显示在登录页，而不是一直停在“连接中”
- 主连接与媒体/CDN 下载统一走 TCP 直连 DC IP——手机系统没有本地 DNS，域名解析会直接失败，IP 直连不依赖 DNS
- 连接断开后自动退避重连（3s→30s），Web 服务不受影响；二维码区域在未就绪时显示进度文字，每 2 秒自动重试，出图后每 20 秒刷新一次

## 在线播放（流式代理）

播放走 Go 后端，前端只消费后端输出的视频流，不直接访问 Telegram：

- **接口**：`GET /api/episodes/{id}/play` 选一路来源后**直接输出视频流**（不再 302 跳转），可加 `?chat=<频道ID>` 固定线路；`GET /api/stream/{sourceID}` 是同一实现的底层地址。宿主播放器不跟随跳转、或跳转后丢 Range/请求头时也不会失败。
- **分块读取（单线程）**：按 `stream.chunk_kb`（默认 512KB，Telegram 单次上限）分块调用 `upload.getFile`，单协程「取一块、写一块、Flush 一块」。Telegram Web 端多线程读同一个文件既不会提速，还会叠加请求触发风控限流，因此已去掉并行预取；拖动/重播靠块缓存命中，不靠并发。
- **块缓存 + 请求合并**：已读块进 LRU 内存缓存（`stream.cache_mb`，默认 128MB），拖动进度条回到看过的位置直接命中；同一块被多个请求同时需要时只向 Telegram 发一次。缓存不放播放进度，因此不会因为每 10 秒上报历史而失效。
- **并发上限**：全局信号量固定为 1，任何时刻最多只有一个 `upload.getFile` 在飞（多播放器/拖动也排队），最大限度降低触发限流/风控的概率。
- **断流重试**：取块遇到网络抖动/瞬时 RPC 错误时按 250/500/1000ms 退避重试（最多 4 次）；响应头已经发出后单块失败会在原地再重试 3 次（300/600/1200ms）才放弃，不再像以前那样一失败就掐断连接让播放器报「播不了」。未登录与 CDN 重定向属于确定性失败，直接返回不重试。
- **Range 语义完整**：支持 `bytes=a-b`、`bytes=a-`、`bytes=-n`，返回 206 + `Content-Range`；越界返回 416；`HEAD` 只回头不回体；带 `ETag` 与 `Cache-Control: private, max-age=3600`，重播/后退不必重新拉流。
- **本地旧缓存优先**：`file_path` 非空时直接 `http.ServeContent`，不占用 Telegram 连接；新版本不再写入视频文件，缓存清空后不会重新下载。
- **侧载规则页优先交给系统播放器**：`tg-drama-rule.html`（`pack.py` 导出，比内置页多一行 `window.__TG_RULE_HOST__` 标记）检测到宿主桥 `window.fm` 时，点播放先把整部剧的播放信息（剧名、封面、简介、全部选集与直链）交给 `fm.vodInline`（带 `mark` 指到当前集，宿主内部失败再退 `fm.play` 单集）；没有这个能力就退到 `fm.play` 只推当前集；两者都不支持才打开页面内置播放器。端口内置页（`/`）不带这个标记，始终用内置播放器，不向宿主推送。两个页面源码都不含任何注释。
- **后端地址判定（侧载页在 TVBox 里能连上的关键）**：`?base=` 显式指定 → `localStorage.tgdrama_base` → 有宿主桥 `window.fm` 时固定用 `http://127.0.0.1:5278` → 无宿主桥且是 http(s) 时同源 → 其余用默认端口。宿主常把 html 放在自己的本地 http 服务上（如 `http://127.0.0.1:9978/file/...`），此时 `location.origin` 是宿主端口，拿它拼 `/api` 只会请求到宿主自己（返回 html），页面就显示「接口连接失败」——所以**有宿主桥时一律优先本机默认端口**。另外启动时会先探一次 `/api/account/state`（拿回 html/解析失败就退回默认端口），任何请求失败也会自动换默认端口重试一次，`video.min.js` 加载失败同样换端口重试；宿主晚注入 `window.fm` 时还会在 `dsready`/`fmsdk` 事件里再校正一次并补拉首屏。

配置（`config.yaml`，可省略用默认值）：

```yaml
stream:
  chunk_kb: 512   # 64~512
  cache_mb: 128   # 8~1024
```

**离开播放页即停止播放**：主站播放页原来只切视图不卸载 `<video>`，返回列表后视频仍在后台缓冲/解码；现在路由切走时先保存进度，再 `pause()` + 移除 `src` + `load()`，并清空剧集/线路状态。

已验证：代理自身吞吐约 4.5–5.2 GB/s（32MB 假数据源，`BenchmarkStreamPipeline`），说明分块/缓存/重组不是瓶颈，真实速度取决于 Telegram 网络；未登录时 `/play` 返回 503 + `{"error":"Telegram 读取失败: 未登录 Telegram，无法在线播放"}`（不再 302 到空流）。

## video.js 播放器 + 直连流

Web 界面已合并为一套：首页 `/` 同时是侧载规则页（`tg-drama-rule.html` 与之同源），登录、频道管理、设置、退出登录都在首页内完成；旧的 `/login`、`/classic` 后台入口重定向到首页。播放器用内置 **video.js** 当内核（`video.min.js` + `video-js.min.css` 随二进制 embed，离线可用），界面与交互按 `lanmei-duanju/internal/app/web` 的竖屏播放器重构，直接消费后端 `/api/episodes/{id}/play` 输出的 MP4：

- **接口**：`GET /api/episodes/{id}/play`（支持 HTTP Range / 206 / ETag），可选 `?chat=<频道ID>` 固定线路；`GET /api/episodes/{id}/lines` 返回每条线路的频道名、可播版本（时长/分辨率/大小）与当前默认线路。旧的 `/hls/*` 接口与 `internal/web/hls.go` 已整体删除，`mp4ff` 依赖也随之移除。
- **播放页**：全屏画面 + 顶部返回/集数/选集 + 右侧倍速/追剧/线路/全屏 + 底部剧名、简介、频道标签、选集胶囊 + 可拖进度条；3 秒无操作控件淡出，触摸/移动唤回。
- **手势**：单击唤出控件，双击暂停/继续，长按临时 2 倍速（松手恢复），上下滑切上一集/下一集，播完自动连播下一集。
- **线路切换**：面板按频道列出同一集的所有版本，并标出「当前」；切换前先校验该频道确实有这一集且有可播文件，切换时记住当前位置，切完从同一进度继续，不回到片头；某条线路取流失败会自动换到下一条有视频的线路，全部失败才提示「这一集暂时播不了」。
- **播放容错**：缓冲超过 15 秒且进度没动、或播放器报错时，先原地重连（块缓存命中，基本无感），再从头重连，再自动换线，三步都失败才亮错误面板；重连/切线路瞬间的 `currentTime` 归零不会覆盖已保存的观看进度。
- **选集/续播**：选集抽屉按集号排布并高亮当前集；`timeupdate` 每 10 秒、暂停、播完、切后台/关页面上报 `/api/history`；重开自动续播（剩余不足 8 秒不跳）；倍速 0.75x–2x 记在本地。
- **不留本地视频**：播放只走 `/play` 的流式 Range 读取，`internal/download` 不再下载视频（只保留历史缓存清理与状态查询），`file_path` 非空的老缓存仍可直接读。
- **选集取正片**：`/play` 先取时长最长的一组；同长度时按文件大小排序取中位数（`pickFromSources`），短预告片和大码率版本都不会成为默认线路。
- **全屏播放**：点封面 ▶ / 选集会在用户手势里同步 `requestFullscreen`，右侧全屏按钮可在全屏与页内之间切换；video.js 加载失败时回退原生 `<video>`。
- **图片全屏查看**：详情页预览图、封面点击后打开全屏查看层（`Esc`/关闭按钮退出，左右按钮或滑动切换，双击/双指缩放，放大后可拖动）。

已验证：`go build` / `go vet` / `go test ./...` 全绿；`TestPickLongestSource` 覆盖「15 秒预告片 + 900 秒正片」，`TestPickMediumSizeWhenSameDuration` 覆盖同长度取中等文件，`TestPickLineSource` 覆盖按频道切线路，`TestStaticAndAPI` 校验 video.js 资源可被后端正常提供。

## 收藏更新提醒

收藏不只是书签，还带「追剧」语义：只有真正追到最新一集的剧，才会在更新时提醒。

- **追剧基线**：`favorites.base_ep` 记录收藏那一刻这部剧的最新集号（有来源的最大集号）。收藏时早就存在的集，无论用户看没看，都不会被算成「更新」。
- **计数口径**（`ListFavoriteShows` / `CountFavoriteUpdates`）：`watched_ep` = history 里这部剧看过的最大集号；`updates` = 大于 `watched_ep` 且已有来源的集数。同时满足 `watched_ep >= 2` 与 `watched_ep >= base_ep` 才计数——还停在第一集（或没开始看）说明只是随手收藏，进度落后于收藏时的最新集也不提示，等他追上来自然会亮。
- **界面**：首页「♥ 收藏」按钮右上角显示所有收藏剧的新增集数合计；收藏卡片左上角红色角标「更新 N 集」，卡片副标题显示「共 N 集 · 看到第 N 集」。看完新集后计数自动归零，不需要手动「已读」。
- **接口**：`GET /api/favorites/summary` 只回 `total` / `updates_total`（首页与关闭播放器时刷新角标用）；`/api/shows?fav=1` 与 `/api/favorites` 也带 `updates_total`，每部剧多 `watched_ep` / `updates` 两个字段。收藏列表的 ETag 混入历史指纹（`HistoryTag`），否则看完一集后列表会被 304 卡住、角标不消失。
- **老库升级**：`favorites` 补 `base_ep` 列，并按当前最新集初始化一次（`kv.fav_base_ep_v1`），不会一升级就冒出成百上千集「更新」。

已验证：`TestFavoriteUpdates` 覆盖「收藏时 2 集 → 只看到第 1 集不提示 → 追上第 2 集后新集计 1 → 看完归零」，`TestFavoriteUpdatesIgnoreWhenBehind` 覆盖进度落后时的静默；真实库副本上实测 6 部收藏、5 部亮角标、合计 10 集，看完最新集后降到 8。

## 排行榜

「🔥 榜单」页签（位于收藏之后、分类之前）抓取五个外部短剧榜单（野果热播榜、51热播榜、黄果短剧榜、黄桃热播榜、黄果热播榜），并把榜单剧名匹配到本地片库，命中才能点开观看：

- **抓取节奏**：默认每 12 小时一轮，走 `telegram.proxy` 代理（榜单站多在墙外，直连会撞 DNS 污染）；抓取结果缓存到 `data/rankings.json`，重启不丢。配置 `rankings.disabled: true` 可整体关闭。
- **匹配原则**：只匹配「可播放」的剧；榜单原排名保留（第 1 条未命中时第 2 条仍显示 #2）；一部剧在单个榜单内只出现一次（保留最好的排名）。
- **匹配规则文件 `data/match-rules.yaml`**：榜单剧名和片库剧名对不上时，用户可以在这个文件里加规则，改完保存即生效（自动热加载，无需重启程序、无需重新打包）。文件不存在时启动会自动生成带完整中文注释的模板；解析出错时保留上一份可用规则并在状态接口里报告问题。五个可配置项（均为可选，删掉某一节不影响其它）：
  1. **别名 aliases**（最直接，推荐优先用）：`"榜单上的名字": "片库里的名字"`，左边命中后直接按右边找剧。适合榜单用了完全不同的译名/简称。
  2. **去尾词 strip_suffixes**：追加要剥掉的装饰后缀（内置已含「完整版/高清版/第N集/第N季」等 24 个）。
  3. **替换 replacements**：正则改写，`pattern` 匹配到的部分换成 `replace`。适合统一去掉前缀、插入分隔符这类批量修整。
  4. **黑名单 blocked_titles**：命中（含去装饰后的变体）就不匹配，用于榜单里混入的推荐位/广告位条目。
  5. **模糊匹配 fuzzy**：默认开启（≥4 字、相似度 0.94，长名 0.88）。两个名字差一两个字也能对上；关掉后只认精确/去装饰命中。
- **自查接口**（改坏了不用猜）：
  - `GET /api/rankings/rules` — 当前规则内容、别名/黑名单条数、问题列表（未知字段、编译失败的正则等）。
  - `POST /api/rankings/rules/test`，请求体 `{"titles": ["榜单上的剧名", "另一个"]}` — 逐条预览命中结果、命中路径（完整名/别名/去装饰/模糊/黑名单）和相似度。
  - `PUT /api/rankings/rules`，请求体为新规则 YAML 全文 — 保存并立即生效；非法 YAML 返回 400 并保留上一份规则。

## 解析与选集规则

剧名、集号和选集归属会影响整库质量，当前规则（重建版本 v43）：

- **剧名双重校验（标签优先）**：正文标题（《》/【】或标题区）与 `#剧名` 标签各取一个候选，归一化后相同或互相包含时**一律采用标签结果**（标签通常是发布者维护的干净剧名，能修《穿过薄雾的早晨2》这类尾数），不一致时才用标题（`#姐姐`、`#剧情` 这类分类词不会变成剧名）；只有标签时用标签，只有标题时用标题。
- **厂牌与水印不进剧名**：`ygwp 小狐仙`、`CBDJ 示例剧`、`9PM剧厂牌水印示例`、`2048原创 快乐星球`、`极乐@jile_ai`、`ReelShort`、`AI大佬自制…` 里的厂牌/水印先剥掉再定名；剥完只剩「动态/正片」+序号的整条不建剧。用户人工确认过的非短剧条目（工具视频、频道名、带番号的片子）列在 `internal/storage/manual_fixes.go` 的隐藏清单里，重算时一并标记 hidden；确认过的同剧异名（如「有五个姐姐的我2」并到「有五个姐姐的我 第二季」）用别名表归并。
- **剧名尾部集号/范围剥离**：`长生录1-10`、`【武侠幻想剧】全12集`、`#亿粉归零第3集`、`示例剧第二季 EP-2` 这类把集号写进名字的，写入前统一剥掉尾部的 `1-10`/`全12集`/`第N集`/`EPn`；没有「第」字的集号（文件名 `长生录 32集.mp4`、`长生录 32.mp4`）和 `_wm`/`_watermarked` 水印后缀同样剥掉（纯数字只对中文名生效，`Squid Game 2` 这类英文续集序号保留）。只有文件名可用的兜底路径也先剥号再判垃圾名，剥完只剩分类词（亲属/角色类泛词）的直接丢弃，不再建出「分类词 第1集」「第一集 水印」这类条目。
- **「第N-M集」整体剥离，不再逐字裁尾**：书名号/方括号里的范围（`《后悔有妻  第1-2集》`、`《远山来信 第十一至十二集》`）以前先删数字再留一个孤立的「第」，建出「后悔有妻 第」这种残名；现在「第 + 数字/中文数字 + 范围 + 集/话/回/合集/合辑/全集」作为完整标记一起剥掉，全角数字与全角分隔符先归一。反过来也不再无条件 `TrimRight("第集期")`——「书香门第」「后会有期」这类合法尾字不会被削成「书香门」「后会有」；孤立「第」没有明确标题证据时不做猜测性裁剪。
- **厂牌前缀/画幅说明词不进剧名**：`AI短剧示例剧名_营销尾巴_推广码718.mp4` 这类文件名，去掉「AI短剧」厂牌标记、末尾「营销尾巴/推广码718/原创最新都市」这类后缀，只留「示例剧名」；`竖屏.mp4`、`ygwp 竖屏.mp4` 只描述画幅，整体判为非短剧丢弃；`示例4_watermarked.mp4` 剥成「示例」后命中分类词，同样丢弃。
- **预告/水印词不建剧**：文件名只剩 `预告_wm.mp4`、`pv预告.mp4` 这类预告/水印词，或名字整条就是 `正片`/`花絮`/`预告片`/`完整版` 的，一律不建剧；正文里的「点此看全」「看到结局」「追更」「N元」等引流话术也算广告名，列表里不会再出现「预告 wm」「HE GOT ME WET 这部后续不在预告里 点此看全」这类条目。
- **水印/搬运号前缀不参与定名**：`阿舞 #韵母攻略 播放第二集`、`西瓜视频~ #剧名 第1集` 这类「短前缀 + 空格 + #标签」，标题候选曾经只剩「阿舞」「西瓜视频」，一部剧被拆成很多水印名。现在标题候选紧挨在标签前面（归一化后是标题的前缀、≤12 字）时，判定它是搬运号/水印，剧名取标签。
- **带标点的 #标签取整行**：`#` 后面只认字母数字会把 `#妈妈，你可是我最爱的人` 截成 `#妈妈`，而「妈妈」在分类词表里会被直接滤掉，剧名整条丢失。现在标准标签都不可用时，按「`#` 到行尾/下一个 #」整段再取一次，首尾标点去掉；`#真人，示例标签` 这类分类词开头的行也不会顶掉正常标题。
- **分类词过滤**：`isGenericTag` 覆盖 100 多个题材/亲属/角色词（真人、剧情、日常、家庭、姐姐、亲属、闺蜜……）。`IsJunkName` 过滤频道水印名与机器名：甄选/最全版/预览/合集、`faststart_sx0d7ra6`、`Qhwfres4nq4kbtc8`、`IMG 9376 MOV`、`play (13)`、`wd1`、`DJ`、纯数字等；拉丁名要过「像单词」校验（长度≥4、元音≥2、无长辅音串），`TheForbiddenFlower`、`Squid Game 2` 这类正常英文名仍保留。重建时对解析出来的名字同样执行该判定，历史库里 80 部垃圾剧（439 条来源）会被清掉。
- **分类词标签不再当剧名**：频道经常不写片名，只在一段口语描述后面挂 `#高颜值 #原相机 #服饰 #穿搭` 这类分类/服饰/广告标签。旧逻辑「无标题容器且标题很长 → 直接取首个标签」会把「原相机」「制服」建成剧。现在：标签若是分类词（genreWords 新增 服饰/穿搭/内衣/写真/生活/自拍/原相机/户外/花絮/片段/完整 等），先退回文件名（剥掉尾部 `第N集`/`EPn`/数字，哈希名丢弃）；标签只是标题去掉尾数/季数时优先用标签；纯口语正文（>14 字或带句读）且没有可用标签时整条丢弃，不再建剧。
- **只有图、名字是分类词的假剧在重建时清掉**：这类剧没有可播集、列表本来就看不见，但会占着搜索和预览图，重建时连同图片一起删除（v31 清掉 77 部、1894 张图）。
- **集号只看标题区**：「剧情介绍 / 简介 / 标签 / 主演」之后的内容不参与集号识别；`第3季`、`第5期`、`EP72分02秒` 不会被当成集号；`1-10集`、`【千金归来】1-10集` 这类无「第」区间也支持。
- **范围帖取第一个有效范围**：`【金牌经纪人】EP3-4 内群连载更新至第12集` 以前会被后出现的「第12集」抢走集号，现在取位置靠前的 `EP3-4`；只有「内群更新至第7集」这类进度说明而没有范围时，才把该数字当兜底集号。
- **合集/合辑也是范围后缀**：`第4-5合集`、`1-6合集`、`第1-8合集`、`EP3-4合集` 以前只认「集/话/回」，匹配失败后集号被后面的「内群更新至第六集」抢走（落成第 6 集），现在 47 条这类文案都能落对起始集。
- **进度说明不覆盖已知集号**：`《剧名》内群更新至第5集` 配文件名 `剧名_EP3.mp4` 时，进度标记 `ProgressEp` 会让位给文件名的第 3 集；只有完全没有别的集号时才用它。
- **连发多集帖按各自的 caption 落集**：频道连发 `第14-15集`、`第16-17集`、`第18-19集` 三条时，Telegram 会把它们的 3 个视频合成一个相册。以前按「组起始集 + 组内序号」计算，得到 14/15/15（后面的都被并进第一段范围）；现在只要成员自己带集号且与组起始集不同，就以自带集号为准，得到 14/16/18。共享一条范围 caption 的正常相册（`EP5-8` + 4 个视频）仍按序号落 5/6/7/8。
- **相册范围优先于文件名**：声明了范围的相册按组内序号落到 `[起, 止]`；成员数多于声明范围时（多码率/水印备份）多出来的算最后一集的分段，不会退回起始集把别集视频混进第 1 集。
- **相册成员不全时用文件名校准**：`《同学的离异妈妈》第3-12集` 是一个 10 视频相册（3494–3503，每个视频一集，caption 挂在最后一条 3503，文件是 `同学的离异妈妈12.mp4`）。如果库里只认得带 caption 的那一条（其余成员还没入库），旧逻辑按「范围起点 + 组内序号」把它记成第 3 集，12 就永远空着；`第13-14集`（3504–3505）同理把 14 记成 13。现在相册里只知道一个视频、且文件名集号落在声明范围内（12 ∈ [3,12]）时以文件名为准；成员齐全时仍按组内序号落 3…12，文件名不在范围内（`720p (13).mp4` 配 `第1-7集`）也不采纳。真实库 `同学的离异妈妈` 由「1-7、9、15-16，缺 8、10-14」恢复为完整 1-18 集。
- **容器只在标题区找，且听 #标签 的**：简介里引用的《别的剧》（「作品简介：《强制怀孕配额法》」）不再被当成本剧名；`【AI&真人联动 示例剧】` 与 `《示例剧》` 同时出现时，由 `#示例剧` 决定取后者。
- **相册成员共享 caption**：caption 常挂在相册最后一条，同步时整页先收集同组 caption 再逐条入库，避免成员先处理读不到 caption 而丢弃。
- **历史丢弃视频复活**：重建时扫描 `raw_messages.info_json` 里的文档信息，把旧版本因「空 caption + 哈希文件名」丢掉的视频补回来源。
- **空 caption 成员也留原文**：v20 批量入库后只有「被接受的来源」才写 `raw_messages`，相册里没 caption、文件名又是哈希串的成员被丢弃后没有任何痕迹，重建也救不回来。现在每个视频消息（含被丢弃的）都会先落一条 `raw_messages`（`info_json` 存文档信息），后到的同组 caption 用 `ON CONFLICT ... DO UPDATE SET text = CASE WHEN raw_messages.text = '' ...` 回填，所以「第7-8集」相册里第 7 集那条能等到 caption 再重试入库，重建时也能把历史丢掉的视频复活。
- **相册内位置按消息 ID 排序**：以前用「已入库成员数 + 组内偏移」算位置，只补到相册中间某条时整体偏移（第 7 集被算成第 8 集）；现在按「库里已有成员 ∪ 本页成员」排序取下标，补拉/补全都不会错位。
- **多标题预览帖按序分配**：一条 caption 依次列了 N 部剧（如《示例剧甲》第6集 《示例剧乙》第7集 …），相册正好 N 个视频时按出现顺序一一对应，不再把 N 部剧的片段都算成第一部剧的同一集。只列了 2 个容器的不算预览帖（多半是「【本剧标题】…简介里引用《别的剧》」），否则会把一部剧拆成两部、集号还会串（`EP1-2` 相册被拆成「ep3 + ep1」）。
- **双扩展名/尾部扩展名先剥掉**：频道里常见 `乐园触手.mov.mp4`，旧代码只去掉最后一层扩展名，清洗后留下「乐园触手 mov」被当成另一部剧。现在 `Parse` 处理文件名前、`CleanFileName` 清洗前后都会反复去掉 `mp4/mkv/mov/avi/wmv/flv/webm/m4v/ts/rmvb` 这类尾部残留，`乐园触手 mov` 会并回 `乐园触手`。
- **日期型剧名直接丢弃**：`10月2日`、`8月4日`、`2024-10-02` 这类按天发帖留下的日期被 `IsJunkName` 拦掉，不再建剧。
- **单集条目的取舍**：`listShowWhere` = 可播 + 排除「仅 1 集且无封面」。判「不是短剧」分三层：①`IsNonDramaSingleName` 名字命中演唱会/广告/众筹/美图/视频消除/宣发/片花/漫展/街拍/vlog/录屏/回放；②来源文案全是社交平台/付费订阅/引流号且**没有**《》/【】容器（`#话题` 不算，`#试衣间` 这类引流话题会被利用）；③**只有 1 集且无法准确识别剧名**（`identifiedShows` 要求来源文案能被当前解析器解析出同名标题或容器名）。命中者由 `RecomputeHiddenShows` 标记 hidden。隐藏只作用于列表：`ListShows/CountShows` 用 `playableShowWhere`（`hidden = 0`），`SearchShows/GetShow` 用 `searchShowWhere`（不看 hidden），所以「无法识别的单集」只藏在列表里，搜索与详情照常可看。真实库：可见 1529 部、hidden 249 部（其中 245 部是无法准确识别的单集）；`浮香楼`、`夜勤综合医院` 等带《》标题的社交帖已恢复显示。
- **合并重复剧时转移预览图与收藏**：`show_photos` 与 `favorites` 没有 `ON DELETE CASCADE`，删除被合并的短剧时会报 `FOREIGN KEY constraint failed (787)`（真实库有 6 部一直合并失败）。现在先把预览图 `UPDATE OR IGNORE` 到目标剧、收藏 `INSERT OR IGNORE` 过去，再删旧剧。
- 改了上述规则要同时把 `internal/storage/rebuild.go` 的 `rebuildVersion` 加一，启动时会自动整库重建（v30 实测 1.42s / 16985 条来源，其中解析 848ms、写库 253ms、分段重编号 115ms，合并 44 部误拆）。
- **例外：只改剧名、不动集号归属的规则不 bump 重建版本**。整库重建按新 norm/集号重新挂来源，名称改变可能生成新 show、删掉旧空集，从而级联删除观看历史、收藏不自动迁移——对「名称残留」这类问题代价过大。这类修正改用下面的 `nameaudit` 定向工具：只原地更新 `shows.name/norm_name`，保留 ID 与全部关联状态。

### 存量剧名修正（nameaudit）

解析规则修好后，历史库里的残名不会自动消失（在线入库遇到已有消息会保留旧来源）。需要修正时用独立离线命令，先看预览再显式应用：

```bash
# 只读预览：不建库、不迁移、不写库，输出 JSON 计划（-output 拒绝覆盖已有文件）
go run ./cmd/nameaudit -db data/tgdrama.db -output name-audit-preview.json

# 确认后显式应用（示例只选一条），先做含 WAL 的一致性备份，失败整批回滚
go run ./cmd/nameaudit -db data/tgdrama.db -apply -ids 14571 \
  -plan name-audit-preview.json -backup data/name-backup-20261113.db

# 名称冲突时把重复剧合并进已有剧（单事务，先备份；保留目标剧 ID/名称）
go run ./cmd/nameaudit -db data/tgdrama.db -merge-from 14572 -merge-into 6728 \
  -backup data/name-backup-20261113-merge.db
```

- 候选只有三类：`eligible`（明确容器标题 + 证据一致 + 仅集号/范围噪声修正）、`review`（证据不足、多标题、来源互相矛盾、纯展示空格变化）、`conflict`（目标 norm 已被别的剧占用，如「后悔有妻 第」→「后悔有妻」撞上已有剧）。`review/conflict` 是「需要人工核对」，不是错误数量。
- 应用只改 `shows.name`/`norm_name` 两列，不动 ID、集号、来源、收藏、历史、标签、图片与 hidden；stale 证据、冲突、未知 schema、名称参与外键/触发器时一律跳过或拒绝，重复执行无变化。
- 合并（`-merge-from/-merge-into`）只接受名字互相包含的两部剧；同集两边都有观看记录、来源唯一键冲突、备份路径已存在时整体拒绝。合并把重复剧的来源并到目标同集（没有同集号则整集搬过去），图片/标签/收藏/观看记录一并转移，最后删除重复剧行；目标剧的 ID、名称、集号与隐藏状态不变。它不重排集号，也不重新解析标题。

## 同步速度与顺序

首次登录后要拉取频道历史，这里做了四层优化（实测 5000+ 条来源）：

- **整页一个事务**：原来每条消息 7 次自动提交（约 700µs/条），现在 100 条共用一个事务并预处理语句（约 100µs/条，7 倍），整库首次同步从数分钟降到几十秒量级。
- **批量预取代替逐条查询**：已入库消息、相册成员数、剧名索引整页/整表一次读进内存，入库时不再逐条 `SELECT`。
- **封面与预览图异步下载**：原来每部新剧、每张预览图都在入库主流程里同步下载（1500 部剧 ≈ 8 分钟纯等网络），现在交给 8 个后台协程，队列满了自动丢弃，交给启动时的补图任务兜底。
- **频道级并发**：3 个频道同时抓取，网络等待重叠；数据库只有单连接，写入仍串行，不会破坏一致性。

入库顺序固定为**频道最早 → 最新**：Telegram 的 `messages.getHistory` 只能从新往旧翻页，没有「从最旧开始」的参数，所以先整段扫描缓存（上限 12000 条，超出分段），再按消息 ID 升序分批入库。这样相册分段编号、范围帖（`EP1-10` 覆盖多个视频）和相册 caption 继承都按时间顺序推进，不会错位；断点仍然记录在 `chats.last_offset_id`（往更旧历史回填）与 `last_top_id`（下次只补拉新增）上。

## 选集补全与规则页手势

### 详情页「🔍 搜索补全」

频道连载时，某一集可能发在另一个频道、或者当初因为「空 caption + 哈希文件名」被丢掉，详情页的选集就会出现空洞。详情页的「选集 N 集」右侧有 **🔍 搜索补全** 按钮，点了才搜（不再打开就自动搜，避免每次进详情都等十几秒）：

- 后端 `POST /api/shows/{id}/fill` 支持 `{"force":true}`：**没有空洞也会搜**。连载剧经常只同步到第 1-2 集，1…最大集号之间没有洞，旧版本直接返回 `{"searched":false,"added":0}`，用户点了也「无效」——这是「搜索补齐无效」最主要的原因。
- `FillMissingEpisodes`（`internal/tgclient/fill.go`）按三轮搜索，前面一轮补到东西就停：① 全局 `#剧名`（`messages.searchGlobal`）② **频道内搜索**（`messages.search` + 每个已收录频道，私有频道/冷门剧全局索引里搜不到，这轮才是真正管用的）③ 全局纯剧名（只写已有频道，避免同名杂帖建新剧）。剧名带空格的（`The Forbidden Flower`）会额外搜去掉空格的写法。
- **相册成员一起补**：搜索只返回带 caption 的那条消息，相册里没 caption 的成员不会出现在结果里。命中的相册再用 `messages.getHistory(offset=消息ID+10, limit=21)` 取回同 `grouped_id` 的成员（相册最多 10 条，窗口要跨过命中消息两侧——caption 挂在第一条时成员 ID 更大，旧版本只往回翻会漏掉整组），单次补全最多 40 个相册。
- **同一条消息只入库一次**：补全会反复命中已经入库的消息，旧版本会按 `segment_index` 再插一条重复来源（同一集出现两份）。`IngestBatch` 现在先按 `(chat_id, message_id)` 查已有来源并跳过，启动时还会清一次历史重复。
- 结果返回 `{added, missing, searched}`：`missing` 是补全**之后**重新算的 1…最大集号空洞（超过 300 集不检查）；未登录返回 `{"error":"未登录 Telegram"}`，30 秒内重复点返回 `{"error":"刚刚搜索过，请稍后再试"}`，这两种都算 HTTP 200。
- 前端：有空洞时显示「选集不连贯（缺 8、10-14 集）」；点补全后补到新集提示「已补回 N 集」并重新拉详情，没补到则提示「未搜到第 8、10-14 集：可能只在付费群/未启用频道发布」。未登录点按钮提示先登录。

### 规则页（`tg-drama-rule.html`）手势

- **顶部下拉刷新**：在页面顶部下拉超过 64px（阻尼 0.6，最大 96px）会显示「松手刷新」，松手后重新拉标签与首屏列表，完成后提示「已刷新」；详情面板打开时、或页面已滚动时不会误触发。
- **回到顶部浮标**：列表往下滚超过 520px 后右下角出现圆形浮标（42px，毛玻璃底、上箭头），点一下平滑滚回顶部；回到顶端、或打开详情/播放器/灯箱时自动收起，不挡封面。
- **清空搜索即回到全部分类**：搜索框内容被删空（退格、输入法清空、`type=search` 自带的 ×）或按 `Esc` 时，自动清掉关键词/标签/模式并重新加载全部短剧，提示「已恢复全部短剧」。
- **详情页预览图**：只显示**最新 3 个有图的集**（`internal/storage/repo_photos.go`：图按消息位置就近归到该频道的视频消息，即集号；取集号最大的 3 集，每集最多 6 张、总共最多 18 张，同集内优先离视频消息最近的图），判不出集号的剧回退为整批最多 18 张。前端排成**一行**（高 140px，宽度按图片真实宽高比计算，横向滑动查看，`scroll-snap` 轻微吸附），图上不叠加集号角标，干净展示画面本身。
- **加载失败/超时自动隐藏**：图片由 XHR 拉取，响应头 `X-Photo-Ready: 1` 才算真图（`0` 表示还是封面/SVG 占位）；从某张图开始加载算起 10 秒内拿不到真图的格子直接撤掉（期间每 1.6 秒重试一次），全部撤完时整条预览区隐藏、不留空白；没有预览图的剧同样不占空间。用 blob URL 展示，切剧时统一释放，灯箱只对当前仍显示的图生效。
- **滚到才加载**：一排 18 张图不再打开页面就同时并发 18 个请求，`IntersectionObserver`（`rootMargin: 300px`）只在格子接近视口时才发 XHR；横向滑到头再加载后面的，请求量随用户实际浏览增长。
- 顺带修掉一个宿主内必现的 bug：桥接调用 `window.fm.req` 时没有把请求体传下去，导致收藏切换、补全这类 POST 在影视 App 里丢参数；现在 `api()` 的桥接分支会带上 `body`。

## 频道管理

采集范围由「频道启用状态」决定：只有 `enabled=1` 的频道会被同步与补全。两个前端都带频道面板，列出全部频道、消息数、视频数与开关：

- **主站**：首页右上角 `⚙` → 「频道管理」；同一面板里还有「预览图缓存 → 清理」（两次点击确认）。
- **规则页**：顶部 `📡` 按钮 → 频道管理抽屉，开关即时生效。
- **启用即同步**：打开开关时后端 `POST /api/chats/toggle` 除了落库，还会调 `Service.KickChatSync`，在后台跑一次「补离线期间的新消息 + 从最新往最旧回填历史」；同一频道同时只跑一份，重复点击返回 `{"syncing":false}`。未登录时只改开关，登录后再同步。
- **手动同步**：`POST /api/chats/sync` body `{"tg_chat_id":<id>}`，让已在采集的频道立刻补一轮（不改启用状态）；未登录返回 503。
- **打开即更新**：打开面板时前端先调 `POST /api/chats/refresh`，服务端现场向 Telegram 拉一次完整对话列表（`Service.RefreshChats`，12 秒超时），新加入或改过名的频道立刻出现；只更新名字/用户名/access_hash，不会覆盖手动开关的启用状态。未登录或拉取失败时退回本地列表，面板照常显示。列表完整拉取成功后还会做一次归属清理：库里存在、但这次对话列表里没有的频道（已退出/被移出）连同其入库数据一起删除，面板不会再显示「已启用」的僵尸频道；停用中的频道也会顺手清掉已入库的数据（频道行保留）。
- **清理预览图缓存**：`POST /api/cache/clear?kind=photos` 删除 `data/photos` 与转码 WebP，并把库里的 `cache_path` 清空（图片下次访问按需重下）；前端按钮改成「点一次变『再点一次确认』、4 秒内再点才执行」——Telegram 内置 WebView 会忽略 `confirm()`，原来的弹窗确认在那里等于点了没反应。
- **列表接口**：`GET /api/chats` → `{list:[{id,tg_chat_id,name,username,type,enabled,message_count,source_count,last_offset,last_top_id,synced_at,syncing}],total,enabled,syncing,refreshed}`，按「已启用优先、视频多的优先」排序。

停用频道会同步删除该频道已入库的数据（`POST /api/chats/toggle` 返回 `purged` 统计），频道行保留以便重新启用；重新启用后从头同步。删除范围：该频道的视频来源与预览图、因此失去全部来源的剧集、失去全部剧集与预览图的剧，以及对应的本地缓存文件；最后 `VACUUM` 收回数据库空间。别的频道也在用的同一集/同一部剧不会误删。
## 常见问题

- **二维码一直不出现/登录无响应**：网络无法直连 Telegram，在配置中填写可用的 SOCKS5 / HTTP 代理
- **手机上扫不了二维码**：登录页点「账号登录」用手机号 + 验证码；**不要**把 PC 的 `data/` 连同 `session.json` 拷到手机——同一个 auth key 从两个 IP 使用会被 Telegram 判重注销，每台设备各自登录一次
- **账号登录提示「操作过于频繁，请 N 秒后再试」**：`auth.sendCode` 被 Telegram 限流。先等限流窗口结束再换号码重试，否则会一直延续；也可改用扫码登录（不走 `auth.sendCode`，不受此限流影响）
- **出现 `API_ID_PUBLISHED_FLOOD` 等限流**：内置默认凭证被过多部署共用触发限流，等窗口结束，或在 config.yaml 换成自己申请的 api_id/api_hash
- **出现 `AUTH_KEY_UNREGISTERED`**：这条会话已被 Telegram 注销（在别的设备上退出了本应用、账号被风控下线，或同一个 session.json 被两个实例共用）。客户端会自动清理本地会话并回到扫码/手机号登录，登录层会提示原因，无需手动删文件
- **下载中断**：程序自动处理 `FLOOD_WAIT` 退避与 `file_reference` 过期刷新，失败任务会自动重试
- **封面不显示**：封面依赖 ffmpeg，请确认系统已安装（`ffmpeg -version`）
- **命名不规范的剧**：无法识别时会用文件名兜底入库，可后续在数据库中人工整理

## 风险提示

- 登录凭证默认内置 Telegram Desktop 官方应用（与参考实现一致），属于共享凭证，可能触发限流或风控；请保持低并发、勿频繁拉取，必要时在 config.yaml 换成自己的凭证
- 用官方 Desktop 凭证登录、同时又以「Web 客户端」的指纹走 WebSocket 传输时，Telegram 可能把这次登录判为可疑并注销账号下的会话（表现为**手机上的 Telegram App 被退出**）。降低这种风险的配置：在 config.yaml 填自己的 `api_id`/`api_hash`（扫码登录不需要收验证码），并把 `telegram.transport` 设为 `tcp`
- 用户账号自动化存在封号风险，请保持低并发、勿频繁拉取，建议使用小号
